## 4. Corrections

1. **The first payload serializer escaped Arabic to `\uXXXX`** in the stored
   outbox payload (System.Text.Json's default encoder) — caught by the
   dispatch test, fixed with `UnsafeRelaxedJsonEscaping` (safe: the payload is
   a DB column parsed as JSON, never embedded in HTML).
2. **The node extraction script's first run returned 0 events** — its bracket
   scan matched the `[]` in the TypeScript type annotation, not the array
   literal. Fixed by anchoring on `= [`. Recorded so the next script-extract
   session doesn't re-derive it.
3. `NotificationSeedData` was first given the placeholder list; the API layer
   cannot see Infrastructure internals, and the vocabulary is contract, not
   seed — moved to `NotificationPlaceholders` in Core.
4. CA1861 (hoist constant arrays) fired on readable inline test arrays — a
   hot-path performance rule with no hot path in tests; disabled for
   `tests/**` in `.editorconfig` with the reason, kept for production code.

BE-06's corrections:

5. **Submit validated the wrong values** — the gate re-read the database for
   values the request had only STAGED (unsaved), so every field failed; and
   then double-staged the per-service rows (unique-index 500). Both mine,
   both caught by the submission test: validate the submitted values, stage
   rows once.
6. I assumed the schema's field ids were kebab-case (`first-name-ar`) and
   that it carried `dependsOn` rows — the workbook's ids are camelCase and
   this version has no conditional fields. The test now reads the served
   schema instead of assuming its shape.
7. `vite-node` hangs in this repo (vite config side effects) — schema
   extraction fell back to the strip-and-eval approach, which needed
   interface/type-alias stripping on top of CAP-07's recipe.

BE-07's corrections:

8. **Sign-in JIT never marked staff as employees** (`is_employee` was
   bootstrap-only, my BE-03-era code) — internal users were invisible to
   committee pools and formation refused them. Caught by all three committee
   tests at once; the flag now follows the provider's internal-role mapping.
9. The interview is APPLICATION-scoped, not per-service as `10` §3.4 drew it
   — the wire contracts (one ticket, one committee, one slot list) decide;
   recorded as an implementation note on the design doc rather than silently
   diverging.

BE-08's corrections:

10. **The send gate queried the database for a signature the same request had
    only STAGED** — so a correctly-signed sequence never reached the
    applicant. The same class of bug as BE-06's submit validation (mine,
    twice now): when a rule reads state the current transaction is still
    writing, the change tracker's local set counts as much as the stored
    rows. Caught by every CAP-03 test at once.
11. A nested collection-expression spread with `?? []` inside it wouldn't
    parse (C# 12); hoisting the parse into a named helper is both the fix and
    the more readable form.
12. **The staged-vs-stored read, three times.** BE-06's submit validation,
    BE-08's send gate and BE-10's offer chain each queried the database for
    state the same request had only staged, and each failed the same way.
    The rule, now written into `OfferService` where the next reader meets it:
    when a rule reads state the current transaction is still writing, the
    change tracker's local set counts as much as the stored rows.
13. **Three scripted edits landed in the wrong place before I checked.** A
    "find the next blank line" heuristic for locating the end of a route
    registration put `.RequireFeature(...)` *inside* two handler bodies,
    because some bodies contain blank lines; and an `optional=True` re-run
    inserted the same `HasData` call twice. Both were caught by the build,
    but the lesson is the cheaper one: anchor a scripted edit on something
    unique and structural (a route's `WithName`, a matched paren) rather
    than on formatting.

13. **The playbook named the wrong risk for BE-11.** Its warning was `Q27`
    (the ERP status list), which turned out to be harmless — a code and its
    labels render as sent and the capability recognises none of them, exactly
    as `P-128` intended. The real blocker was never written down anywhere:
    the ERP payload as specified carries **no programme reference**, so
    `BR-0602`'s third hop has no source and `BR-0603` hides every record from
    every trainer. Raised as `Q39` (`P-197`). The lesson is not about ERP —
    it is that a prompt's ⚠️ line is the risk somebody *anticipated*, and
    reading the contract's own field list against the rule it has to satisfy
    is what finds the one nobody did.
14. **The temptation, named so the next session does not fall for it.** With
    hop 3 unsourced, linking "the trainer's only recent engagement" would
    have made the demo work and every screen fill up. It was not done: a
    fabricated link attaches real money to a programme nobody confirmed, and
    that is worse than an empty screen with a documented reason.

15. **The dashboard contract carried an assumption nobody had noticed.**
    `DashboardMetricDto.status` was typed `ApplicationStatus` because all
    four existing tiles drilled into the application inbox. `F-0902`'s third
    tile counts material submissions, which have no application status — so
    the field could not be filled truthfully for it. Corrected to a
    discriminated `target` rather than by widening the status union, which
    would have let a submissions tile carry `'under-review'` and mean
    nothing by it. Worth recording because the assumption was invisible
    while every member of the set happened to satisfy it.
16. **I nearly under-delivered this increment on a technicality.** The
    reasoning went: `Q26` asks whether `F-0902`'s tiles are the approved set,
    the answer is open, therefore do not build the third one. That is the
    wrong shape of caution — the BRD *names* those three, so building them is
    following the specification, and the open question is whether MORE are
    wanted. The gap to leave open was the coordinator's and executive's
    metrics, which the BRD genuinely does not define. Naming an unanswered
    question is not a reason to skip the part that IS answered.

## 7. Environment traps (this session's additions)

- System.Text.Json escapes non-ASCII by default — anything asserting on
  stored Arabic JSON needs the relaxed encoder or decoded comparison.
- Extracting a TS array literal by bracket-matching must anchor after `= [`,
  or the type annotation's `[]` wins.
- The Bash tool can mangle `\u` sequences inside heredoc'd python strings —
  use raw strings (`r'''`) for content containing backslash-u.
