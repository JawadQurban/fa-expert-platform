### Review result (backend/expert-hub, ASP.NET Core 9 + EF Core 9)

Build 0 warnings; tests 302/302 pass in 2m58s on LocalDB. Async hygiene is clean
(cancellation tokens forwarded, no sync-over-async), DI has no captive dependencies.
Defects worth fixing before UAT sign-off, each verified against the code:

- **Catch filters swallow HTTP timeouts.** `when (ex is not OperationCanceledException)`
  also filters `HttpClient.Timeout`'s `TaskCanceledException`:
  `FastApiClient.cs:191`, `AiAnalysisChannel.cs:100`, `OutboxPublisher.cs:73`/`:112`,
  `FastProfileImport`. In the outbox publisher it faults `ExecuteAsync`, and .NET's
  default `StopHost` then stops the API; the attempt is never saved, so the same
  message fails first again after restart.
- **Screening 500 on repeated sections.** `ScreeningEndpoints.cs:570` keys a dictionary
  on `FieldCode` alone; the M34 change stores one row per entry (`EntryIndex`). Any
  application with two entries cannot be opened or decided. No test covers it.
- **One trainer can take every slot of a request.** `OfferService.cs:75-84` excludes
  engaged trainers but not those holding a live offer on a sibling slot.
- **No concurrency tokens anywhere** → double-submit races on pool decision, signing
  sequence formation, applicant sign, lifecycle renew/end, and interview completion
  (`InterviewEndpoints.cs:215-224`, where the interview can stick in `Scheduled` for ever).
- **Business days counted on the UTC weekday** (`BusinessCalendar.cs:18`); Riyadh is +3,
  so an offer sent 00:00–03:00 Thursday Riyadh falls due on a Friday.
- **Expiry sweep has no per-offer catch** (`OfferService.cs:339-351`): the earliest-due
  offer is processed first, so one bad row blocks every later expiry.
- **Authorization:** attachment download gated on `IsEmployee`, a FAST flag never
  revoked (`ApplicationEndpoints.cs:357`); certificate removal has no `RuleCode` filter
  and can delete the CV link (`ProfileEndpoints.cs:430`); `SafeRelativePath` allows
  control characters (`AuthEndpoints.cs:165`); session tickets are stored unprotected
  (`DatabaseTicketStore`, claims + id_token in plaintext) though the DbContext comment
  says "encrypted"; the id_token is sent to the SPA (`AuthEndpoints.cs:209`); an F-0802
  holder can grant themselves system-administrator (`AccessEndpoints.cs:231-298`,
  latent — only sysadmin holds F-0802 in the seed).
- **Also:** three `new HttpClient()` singletons with no `PooledConnectionLifetime` and
  default 100s timeouts; whole-table loads (candidate search, users⨝roles three times
  per committee GET, the anonymous directory on every hit, `/users` unbounded);
  max+1 / count+1 reference numbers collide into a 500; no filtered unique index for
  one draft per applicant; a database failure at sign-in is swallowed with no log
  (`AuthenticationSetup.cs:413`); no OpenAPI; no rate limiting; no CI at all.

Rejected as not worth it here: interface-per-service, flipping the DbContext to
NoTracking by default (would silently no-op existing tracked updates), and a
`TypedResults` migration without OpenAPI.
